# IT-Index v2 要件定義書 — ハイブリッド再設計

- 版: 0.1（2026-08-09。初版・レビュー前）
- 前提: [v1 要件定義書](../requirements.md) — v1の目的・用語定義はそのまま引き継ぐ。本書は**v1からの変更点と、その根拠**を中心に書く

---

## 1. なぜ作り直すか

v1で「実装不可能・断念」になった機能を棚卸しした結果、その大半は個別の技術問題ではなく、
**最初期の設計思想「サーバーを持たない」（v1 [requirements.md §3](../requirements.md)）という1つの決定**に根本要因が集約されていた。

| v1で断念・制約された機能 | 直接の理由 | サーバー不在との関係 |
|---|---|---|
| Anthropicアカウントログイン | サードパーティOAuthの禁止（v1 §7） | サーバーがあればAPIキーをサーバー側で保持し、独自アカウントで代替できた |
| 端末間同期（PWA時代のLAN直結） | ブラウザは待ち受け・mDNS・http直結が不可（v1 §5.5） | サーバーが無いため端末同士の直結しか手段がなく、Electron化という根本転換で解決した |
| 共有フォルダ同期（Android） | File System Access API未対応（[manual-sync.md §4](../manual-sync.md)） | サーバー同期があれば不要だった迂回策 |
| Google Drive同期 | OAuth同意画面の審査・運用負荷で休眠（[drive-sync.md](../drive-sync.md)） | 自前同期サーバーの代替として選んだ結果の袋小路 |
| APIキー暗号化（WebAuthn PRF→置換） | 端末環境依存で失敗しやすい（[data-layer.md §鍵](../data-layer.md)） | キーを端末に置くこと自体がサーバー不在の帰結 |

加えて、保守性の構造問題（CIの長期不在、PC/Android UIの並行実装による大規模重複、
`App.tsx` 659行への責務集中、同期のトランザクション原子性未達、ビルド生成物のコミット混入）が
[2026-08-09のUI手触り検証](../review/2026-08-09-UI手触り検証.md)等に記録されている。
**v2は機能追加とこれらの構造問題の解消を、1からの作り直しで同時に行う。**

## 2. v2の設計思想 — 「所有はローカル、調整だけサーバー」

v1の「サーバーを持たない」を、**v1自身が2026-08-02に訂正した表現「料金のかかる外部サーバーを持たない」**（v1 §7:
「無料枠で完結する中継の設置自体は禁じていない」）まで戻し、そこから再出発する。

> **データの所有と主機能はローカル（v1と同じ）。端末間の調整（同期・鍵の保管）だけを、無料枠で動く薄いサーバーが担う。**

| 原則 | 内容 | v1からの変化 |
|---|---|---|
| **ローカルファースト** | 検索・閲覧・履歴・ノート編集は端末内Dexieで完結。通信なし・無料・無制限 | 変わらない |
| **オフライン動作** | サーバーが停止しても、検索・閲覧・編集・履歴は動く。同期とAIだけが止まる | 変わらない（v1の可用性要件を維持） |
| **同期はサーバーリレーに一本化** | LAN直結・Drive・手動ファイル書き出しの3方式を全廃し、リレー1本に置き換える | **変更**。v1は3方式が併存 |
| **APIキーは既定でサーバー側で保持** | AI呼び出しはサーバー経由（AIプロキシ）。既定では端末にAPIキーを置かない。**例外として、利用者が自分のキーを持ち込む選択肢を残す**（下記） | **変更**。v1は端末内暗号化（safeStorage / Android Keystore）が唯一の方式 |
| **費用ゼロを維持** | サーバーは無料枠で動くものに限定。無料枠を超える設計になったら、その機能を削る側に倒す | 表現の再解釈 |

> **提供形態による違い（2026-08-12追記）**: 上表の「同期はサーバーリレーに一本化」「APIキーは既定でサーバー側で保持」は、
> **公式ホストでは有償（ライセンス必要）** な範囲を含む。セルフホストでは運用主体=利用者自身のためライセンス概念が無く、
> 上表のとおり無料で動く。形態の定義とライセンスの範囲は [§4「提供形態」](#4-提供形態) を参照。

#### 利用者が自分のキーを持ち込む選択肢（BYOK。2026-08-11追記）

原則は上表のとおり「APIキーはサーバー側で保持」だが、**利用者が自分のAPIキーを設定して使う経路を任意の追加として持つ**。
運営者負担の回数上限に縛られたくない利用者と、サーバーの運用プロバイダ（現在はOpenAI）以外を使いたい利用者のための逃げ道である。

| 観点 | v1 | v2 |
|---|---|---|
| 端末へのキー保存 | **唯一の方式**。端末内暗号化（safeStorage / Android Keystore / WebAuthn PRF）に苦労し、環境依存の失敗で断念した（§1） | **任意の追加経路**。既定はサーバー側キーで、持ち込みは利用者が選んだ時だけ |
| 保存の形 | 暗号化を目指した | **平文のlocalStorage**。暗号化は再現せず、被害の有限化（プロバイダ側の支出上限設定の案内）に寄せる |
| プロバイダ | 端末から直接呼ぶ前提でプロバイダ固定 | 利用者が選べる（OpenAI / Anthropic）。呼び先はサーバーの `AI_PROVIDER` と独立 |
| 回数上限 | （サーバーが無いため概念なし） | **持ち込みキーには適用しない**（費用が本人負担のため）。サーバー側キーの経路では必ず効く |
| 設定の確かさ | 形式の即時検証・接続テスト・エラーの日本語翻訳（§5.7） | **接続テストを保存の前提にする**。上流へ最小のリクエストを1件投げ、通った時だけ端末に保存してチャットに使う |

**動作保証はしない。** 接続テストが通ったキーなら使えるが、OpenAI以外のプロバイダは実動作の確認をしておらず応答品質は保証しない
（この旨を設定画面に明記する）。詳細な契約は [architecture.md §5「3つの経路」](./architecture.md)。

### この思想で可能になること・ならないこと

| 項目 | v2での扱い |
|---|---|
| 全端末同期（Android含む・LAN外でも） | **可能になる**。リレー経由のため同一LAN制約が消える |
| APIキーを端末から排除 | **既定では可能になる**。keystore/・WebAuthn断念の系譜の問題を根本解消。ただし利用者が自分のキーを持ち込む場合のみ端末保存に戻る（本人の選択・平文・支出上限の案内付き） |
| 独自アカウント | **最小限で導入**。同期とキー利用の本人識別のためだけに置く |
| Claude Code定額プランでのAIチャット | **引き続き不可**。Agent SDKの常駐Nodeプロセスは無料枠サーバーレスに載らない。判断はv1 [ai-client.md §定額プラン](../ai-client.md)を踏襲 |
| Anthropic OAuthログイン | **引き続き不可**（Anthropic側の禁止事項。v1 §7）。独自アカウント+サーバー側キー保持で目的を代替する |

## 4. 提供形態

v2は同じサーバー実装（`v2/server`）を、**2つの形態**のいずれかで動かして使う。

| 形態 | 内容 |
|---|---|
| **セルフホスト** | 利用者が自分のCloudflareアカウント等にサーバーを立てる（[deploy.md](./deploy.md)）。公式ページ、または自前で配信するクライアントの「接続先サーバー」設定（次PRで実装予定）から、自分のサーバーのURLを指定して使う。運用主体は利用者自身 |
| **公式ホスト** | 運営者が運用する環境（`https://it-index.doryu.workers.dev`）をそのまま使う。**同期**と**共有AI（運営者キーでのAI利用）は有償**で、ライセンスコード方式で提供する |

クライアントの配布形態はWeb（ブラウザ）に加え、v1同様のAndroidアプリ（APK。[deploy.md §7](./deploy.md#7-androidアプリのビルド)）も提供する。接続先は既定で公式ホストだが、アプリ内の「接続先サーバー」設定で自分のセルフホストへ切り替えられる（appIdはv1（`com.itindex.app`）と別の`com.itindex.v2`のため共存する）。

セルフホストでは運用主体=利用者自身であり、「運営者キーを他人に使わせる」構図が存在しない。そのため
セルフホストにライセンスの概念は無い（サーバー側のライセンス確認は`LICENSE_ENABLED='0'`で止められる。
[deploy.md「運用ノート」](./deploy.md)）。以降、本書・[architecture.md](./architecture.md)・
[deploy.md](./deploy.md)で「ライセンス」と言うときは常に**公式ホスト利用時**の話を指す。

### 4.1 無償/有償の機能線引き（公式ホスト利用時）

| 機能 | 要否 |
|---|---|
| アカウント作成 | 無料（本人識別のみ） |
| ローカル全機能（検索・索引・履歴・詳細・チャット履歴のローカル保存） | 無料 |
| BYOK（自分のAPIキー）でのAI利用 | 無料。ライセンス不要（§2「BYOK」） |
| 端末間同期 | **ライセンス必要** |
| 運営者キーでのAI利用（上限あり） | **ライセンス必要** |

セルフホストでは全機能が上表の「無料」側の扱いになる（運用主体=利用者自身のため、同期も運営者キーでのAI利用も
ライセンス確認なしに動く設計にする）。

### 4.2 決済はモック（現時点）

「登録 → ライセンスコード発行 → 決済確定」という画面フローは実装するが、**実際の課金は行わない**（現時点ではモック）。
ライセンスコードは、デモ用の便宜的な仕組みではなく**正規の製品仕様**として位置づける。サーバー側の`licenses`テーブル
（発行と有効化を分離する設計。[architecture.md §5](./architecture.md)）は、決済が実課金に置き換わっても変更不要な形で
設計する（サーバー側の発行・有効化API=`/api/license/purchase`・`/api/license/activate`は実装済み。購入・入力の
画面フローも実装済み——設定タブ「購入手続きへ」から、まず「月額サブスクで何ができるか」の説明画面を挟み、
Stripe Checkout風の全画面カード入力（`CheckoutScreen.tsx`）へ進む（#151。設定タブのライセンス欄にも
同内容のヘルプ（`LicenseHelpModal.tsx`）を置く。特典の文言は両者で共有し、本節の「ライセンスで有効になる
2機能」以外は記載しない）。カード番号・CVCの検証はフロント側で完結し**サーバーへ送らない**。表示用の4項目（ブランド・下4桁・
有効期限・名義）だけは`payment_methods`テーブルに**アカウント単位で保存**し、設定タブにライセンスコード・
お支払い方法・課金開始日/次回請求日（カード変更導線含む）を表示する）。
実際の課金・実カード情報の取扱いは当面導入しない（導入時期未定。入力画面にも「実際のクレジットカード番号は
登録しないでください」と明記する）。

**表示情報をサーバーに置く理由**（当初は端末内localStorageのみだった。#144で変更）:
ライセンスの有効/無効はアカウント単位（`licenses`）で判定するため、購入した端末以外では
「ライセンス有効なのにカード未登録」という矛盾した表示になっていた。有償機能が端末間同期である以上、
複数端末の利用者ほど必ずこの状態に当たる。保存先をサーバー1箇所に寄せ、端末を変えても
**どのカードから引き落とされているかが分かる**ようにする。完全なカード番号とCVCは、
端末にもサーバーにも保存しない方針を維持する（`payment_methods`にその列は無い）。

### 4.3 解約

設定画面の最下部に解約導線を置く。取り消せない操作のため、オールクリアと同じ
**確認パネル→確認文字列の完全一致**の二段確認を必須にする。

解約（`POST /api/license/cancel`）は**即時無効**で、次が同時に起きる:

- `licenses.canceled_at`が立ち、端末間同期と運営者キーでのAI利用がその場で使えなくなる
  （判定は`hasActiveLicense`の1箇所に集約されているため、表示だけ解約済みで実権限が残ることはない）
- 登録中のお支払い方法（`payment_methods`の行）を削除する。解約後は「引き落とされるカード」が存在しないため
- **解約したライセンスコードは再利用できない**（`code`はPRIMARY KEYのまま残り、再有効化を弾く）。
  再開は新規購入=新しいコードの発行になる

解約に日次試行上限（購入・有効化に課しているもの）は**かけない**。解約を回数制限で妨げる作りは
製品として不適切なため。

## 5. 機能要件 — 要不要の判断

### 5.1 残す（コア価値。v1の設計をそのまま引き継ぐ）

| 機能 | v1の該当 | 備考 |
|---|---|---|
| 用語検索（かな入力で漢字も英字も） | §5.1 | 純関数コア（normalize/score/kanaRow）は**そのまま移植**する |
| 辞書が育つ2枠分離（summary不変+AI補足） | §5.2 | データモデルごと引き継ぐ |
| AIチャットと分配統合 | §5.3 | 呼び出し経路だけAIプロキシ経由に変わる |
| 重み付け（苦手分野の可視化） | §5.4 | asksのログ+和集合設計を引き継ぐ |
| シード取り込み | §5.7 | 検証に通らなければ中止、の原則も引き継ぐ |

### 5.2 新規・置き換え

| 機能 | 置き換え対象 | 内容 |
|---|---|---|
| **サーバーリレー同期** | LAN直結ペアリング／Drive同期／手動ファイル書き出し | 端末はリレーへ差分を送受信。マージは端末側で決定的に行う（v1の冪等マージ設計を同期プロトコルへ昇格）。**公式ホストでは要ライセンス**（セルフホストは不要。[§4](#4-提供形態)） |
| **独自アカウント** | （新規） | 同期グループとキー利用の本人識別。メール+パスワード等の最小構成。マルチユーザー共有は引き続き対象外 |
| **AIプロキシ** | 端末内APIキー保管（keystore/） | サーバーがAPIキーを保持し、認証済み利用者のリクエストを転送。段階導入（Phase 2）とし、Phase 1では暫定的にv1同様の端末内保管を許す。運営者キー経路は**公式ホストでは要ライセンス**（セルフホストは不要） |
| **自分のAPIキーの持ち込み（BYOK）** | v1の端末内APIキー保管（唯一の方式だった） | 任意の追加経路。プロバイダ（OpenAI / Anthropic）とモデル名を利用者が選び、**接続テスト（`POST /api/ai/test`）に通った時だけ端末に保存**してチャットに使う。端末保存・回数上限なし・費用は本人負担。動作保証はしない（§2の表）。**ライセンス不要**（公式ホスト・セルフホストいずれでも） |
| **単一レスポンシブUI** | src/ui/pc/ と src/ui/android/ の並行実装 | 1コンポーネント一式で全画面を賄う。v1最大の重複の解消 |

### 5.3 廃止（v2に持ち込まない）

| 廃止するもの | 理由 |
|---|---|
| Google Drive同期（drive/） | 休眠中・OAuth審査の運用負荷で実運用不能。リレー同期が代替 |
| LAN直結ペアリング（pairing/、電源側HTTPサーバー含む） | リレー同期が代替。同一LAN制約・ペアリング操作の複雑さが消える |
| 手動ファイル書き出し同期（manualSync/） | 同上 |
| WebAuthn PRF残滓 | v1で既に置換済み。v2はキー自体を端末に置かない |
| 端末内APIキー暗号化（keystore/） | AIプロキシ導入（Phase 2）で不要化。Phase 1の暫定期間のみ簡易版を残す |
| e2e/investigate-*（使い捨て調査スペック） | ゲートとして機能しない混入物。v2のテストスイートに入れない |
| release/ 等のビルド生成物のコミット | .gitignoreで最初から除外。lint機能不全の直接原因だった |

## 6. 非機能要件

v1 §6 を基準に、変更点のみ:

| 区分 | v2の要件 | v1からの変化 |
|---|---|---|
| 可用性 | **サーバー停止時も検索・閲覧・編集・履歴が完全に動く**。同期とAIのみ不可 | 「鍵が無くても」に加えて「サーバーが無くても」を明文化 |
| データ保全 | 同期の取り込みは**Dexieトランザクションで原子的に**行う。途中失敗でロールバック | v1で未達だった要件（[drive-sync.md §課題](../drive-sync.md)）を**必達**に格上げ |
| セキュリティ | APIキーはサーバー側のみ。端末⇔サーバーは認証必須。学習データの中身をサーバーに平文で長期保存しない設計を優先検討（詳細は architecture.md §6） | 「漏れても被害が有限」の思想は維持し、境界をサーバーに移す |
| 費用 | 検索・閲覧・履歴は完全無料（v1同様）。**サーバーは無料枠内で運用**。超えそうな機能は削る（ここでの「費用」はサーバー運営コストの話。公式ホストの同期・運営者キー利用に対する利用者への課金＝ライセンスとは別軸。§4） | サーバー費用ゼロを要件化 |
| 保守性 | **CI（型検査・lint・単体テスト・E2E）を最初のコミットから有効化**。純関数コアの単体テスト固めはv1を踏襲 | CI初日導入を要件化 |

## 7. 対象外（やらないこと）

| 対象外 | 理由 |
|---|---|
| iPhone / iPad / macOS Safari | v1から変わらず |
| 料金の発生するサーバー運用 | 無料枠超過が見えたら機能を削る側に倒す（これは運営コストの話。利用者への課金＝ライセンスは対象外ではなく§4で扱う） |
| Claude Code定額プランでのAIチャット | 常駐Nodeプロセスが必要で無料枠サーバーレスに載らない |
| Anthropic OAuthログイン | Anthropic側の禁止事項（v1から変わらず） |
| 複数ユーザーでの用語共有 | 個人の学習記録という性格はv1から変わらず。アカウントは本人識別のみに使う |
| 用語の自動リンク化・手動編集 | v1の判断を踏襲 |
