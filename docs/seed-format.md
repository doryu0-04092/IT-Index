# 初期データ（シード）形式仕様

IT-Index の辞書に最初から入っている用語データの形式を定める。

**この文書の目的は、データを作る前に形式を確定させること。** 数百〜千語を作った後で形式の食い違いが判明すると、全件やり直しになる。

- **配置**: `public/seed/terms.json`
- **配信**: GitHub Pages 上に静的ファイルとして置き、アプリが初回起動時に取得する
- **作る人**: 本人（AIには生成させない）

---

## 1. ファイル全体の構造

```json
{
  "schemaVersion": 1,
  "version": "2026-07-24",
  "terms": [
    { "term": "...", "readings": ["..."], "summary": "...", "field": "...", "tags": ["..."] }
  ]
}
```

| フィールド | 必須 | 型 | 説明 |
|---|---|---|---|
| `schemaVersion` | ✅ | number | **この仕様のバージョン。** 形式そのものを変えたときに上げる。アプリはこれを見て、知らない値なら取り込みを中止する |
| `version` | ✅ | string | **データの版。** `YYYY-MM-DD` 形式。中身を1文字でも直したら更新する |
| `terms` | ✅ | array | 用語の配列 |

### `version` の役割 — 差分更新の判定に使う

アプリは取り込んだ `version` を記録しておき、**配信された `version` が記録と違うときだけ**取り込み処理を走らせる。同じなら何もしない。

> **重要**: 初期データを更新配信しても、**利用者のAI補足（`notes`）は一切影響を受けない。** 用語とAI補足は別テーブルで管理しているため。安心して差し替えてよい。

---

## 2. 用語1件の形式

```json
{
  "term": "TCP/IP",
  "readings": ["ティーシーピーアイピー"],
  "summary": "通信の取り決めを層に分けた規約の集まり。インターネットの基盤。",
  "field": "ネットワーク",
  "tags": ["プロトコル"]
}
```

| フィールド | 必須 | 型 | 説明 |
|---|---|---|---|
| `term` | ✅ | string | **見出し語。** 表示にも検索にも使う。ファイル内で重複禁止 |
| `readings` | ✅ | string[] | **読み。** 詳細は §3 |
| `summary` | ✅ | string | **簡潔な説明。** 詳細は §4 |
| `field` | ✅ | string | **分野。** §5 の一覧から必ず選ぶ |
| `tags` | — | string[] | 任意のキーワード。省略可。無ければ書かなくてよい |

### `id` は書かなくてよい

アプリが `term` から決定的に生成する（正規化した文字列をキーにする）。手で管理する必要はない。

**ただし `term` の重複は禁止。** 重複があると同じ `id` になり、取り込み時にエラーで止まる。

---

## 3. `readings` — 読み

### 付ける対象は2種類

| 対象 | 例 | なぜ必要か |
|---|---|---|
| **漢字を含む語** | 暗号化 → `アンゴウカ` | **漢字が読めないから引く**、という本来の使い方を成立させる |
| **英数字の語** | API → `エーピーアイ`<br>TCP/IP → `ティーシーピーアイピー` | **かな入力だけで英字の用語を引けるようにする。** 日本語話者にはこれが効く |

**カタカナだけの語も付ける**（`サーバ` → `サーバ`）。全語に必ず1つ入れる。

### 揺れは列挙しない。主要な1つだけ

略語は読みが揺れるが（SQL＝エスキューエル／シークェル）、**代表的な1つだけ**を書く。

| 3段で受け止まるので1つで足りる |
|---|
| ① 読みで引く … `えすきゅーえる` → SQL |
| ② **英字で引く** … `sql` / `SQL` → SQL（見出し語がそのまま検索対象） |
| ③ **AIに聞く** … 「シークェルって何」→ チャット |

配列なのは検索の実装都合。**原則1要素**で書く。

### 表記ルール

- **カタカナで書く**（アプリ側でひらがなに正規化するので、どちらでも動くが統一する）
- 長音「ー」はそのまま書いてよい。検索側が吸収する
- 記号は入れない（`TCP/IP` の読みに `/` は書かない）

---

## 4. `summary` — 簡潔な説明

### 役割は「思い出す」。理解させるためのものではない

IT-Index の用語詳細は2枠に分かれている。

| 枠 | 中身 | 誰が書くか |
|---|---|---|
| **`summary`（この項目）** | **思い出すための簡潔な説明** | **本人（不変。AIは書き換えない）** |
| AI補足 | 理解するための、単独で読める完結した説明 | AI（使うたびに育つ） |

**`summary` は「分かる人が見れば思い出せる」水準で止める。** 分からない人を理解させるのはAI補足の役割であり、ここで頑張る必要はない。

### 目安

- **1〜2文、80文字以下**（短くても、意味を取り違えない説明になっていればよい）
- 何であるかを言い切る。前置きを書かない
- 前提知識の説明・具体例・比喩は**書かない**（それはAI補足の領分）

| | 例 |
|---|---|
| ⭕ 良い | `通信の取り決めを層に分けた規約の集まり。インターネットの基盤。` |
| ❌ 長すぎ | `TCP/IPとは、インターネットで広く使われている通信プロトコルの集まりのことで、アプリケーション層・トランスポート層・インターネット層・リンク層の4階層に分かれており、それぞれが独立した役割を…` |
| ❌ 曖昧 | `ネットワークの基本的な概念。` |

---

## 5. `field` — 分野

**必ず下記から選ぶ。自由記述にしない。** 表記が揺れると絞り込みも集計も壊れる。

基本情報技術者試験のシラバス（中分類）に合わせる。

### テクノロジ系

`基礎理論` / `アルゴリズムとプログラミング` / `コンピュータ構成要素` / `システム構成要素` / `ソフトウェア` / `ハードウェア` / `ヒューマンインタフェース` / `マルチメディア` / `データベース` / `ネットワーク` / `セキュリティ` / `システム開発技術` / `ソフトウェア開発管理技術` / `AI`

### マネジメント系

`プロジェクトマネジメント` / `サービスマネジメント` / `システム監査`

### ストラテジ系

`システム戦略` / `システム企画` / `経営戦略マネジメント` / `技術戦略マネジメント` / `ビジネスインダストリ` / `企業活動` / `法務`

> **この24分類で確定（`AI` を 2026-07-24 に追加）。** アプリはこの一覧をそのまま検証に使うので、**この節が正本**。
>
> **`AI` はIPAシラバスの中分類ではなく、本アプリ独自に設けた分野**（AI・機械学習関連の用語を独立させるため）。
>
> **細かすぎると分かった時点で、大分類3つ（テクノロジ系／マネジメント系／ストラテジ系）へ集約する。**
> 上の見出しが示すとおり、23の中分類はいずれか1つの大分類に属するため、**集約は機械的に行えて既存データを壊さない**。逆（3→23）は手作業になるので、迷ったら**細かい方で始めるのが安全**。

## 6. 記入例

3パターンを実際に示す。**説明より例の方が伝わる。**

```json
{
  "schemaVersion": 1,
  "version": "2026-07-24",
  "terms": [
    {
      "term": "暗号化",
      "readings": ["アンゴウカ"],
      "summary": "データを第三者に読めない形に変換すること。鍵を持つ相手だけが元に戻せる。",
      "field": "セキュリティ",
      "tags": ["暗号"]
    },
    {
      "term": "API",
      "readings": ["エーピーアイ"],
      "summary": "ソフトウェアの機能を外部から呼び出すための窓口。内部の作りを知らなくても使える。",
      "field": "ソフトウェア"
    },
    {
      "term": "TCP/IP",
      "readings": ["ティーシーピーアイピー"],
      "summary": "通信の取り決めを層に分けた規約の集まり。インターネットの基盤。",
      "field": "ネットワーク",
      "tags": ["プロトコル"]
    }
  ]
}
```

- **1件目（漢字語）**: 読みが無いと引けない典型
- **2件目（英字語）**: かな入力で引けるようにカタカナ読みを付ける。`tags` は省略してよい
- **3件目（記号を含む語）**: 読みに `/` は書かない。`TCPIP` と打っても検索側が吸収する

## 7. 作成の進め方（提案）

数百〜千語すべてに読みと説明を付けるのは重い。**分業を推奨する。**

1. **用語リストと `field` を先に確定させる**（本人）
2. **`readings` と `summary` の下書きをAIに一括生成させる**
3. **目視で修正する**（本人）— 特に `summary` が長すぎないか、`field` が一覧内かを確認
4. `version` を付けて `public/seed/terms.json` に配置

> **AIに生成させるのは下書きまで。** 試験内容として正しいかの判断は本人が行う。ここは辞書の信頼性に直結する。

---

## 8. 取り込み時にアプリが行う検証

以下に1つでも違反があると、**取り込みを中止して既存データを保持する**（壊れたデータで上書きしない）。

| 検証 | 違反時 |
|---|---|
| `schemaVersion` が既知の値か | 中止 |
| `term` / `readings` / `summary` / `field` が全件に存在するか | 中止 |
| `readings` が1要素以上あるか | 中止 |
| `field` が §5 の一覧に含まれるか | 中止 |
| `term` の重複が無いか | 中止（重複した語を表示） |

検証を通ったら、`searchKey` と `readingKeys` を計算して保存する（正規化: かな統一／全角半角／英字大小）。

---

## 9. この形式を再利用する変更データ層

利用者が Claude Code などのAIエージェントで編集する「変更データ層」（`origin:'ai'` の語）も、この文書と**完全に同一の形式**を使う（`id`/`searchKey`等を書かない、24分類から選ぶ、等のルールもすべて共通）。異なるのは配置場所（アプリ内蔵ではなく利用者が選んだローカルフォルダ）と、`summary` が空文字を許容する点（後方互換のため）のみ。詳細は [local-data.md](./local-data.md) を参照。
