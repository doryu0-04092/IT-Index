## [1] ダークテーマでプライマリボタン等の白文字がWCAG AA未達（コントラスト比2.41:1）
- 種別: ゲート違反
- 画面: search / detail / chat / history（`.btn-primary`, `.chat-message-user`, `.history-tabs button.active` を使う全画面）
- 現象: ダークテーマの `--accent: #6ea8fe`（`src/index.css:32,50`）を背景に白文字（`color: white`）を乗せる3箇所（`.btn-primary` `src/index.css:108-112`、`.chat-message-user` `src/index.css:621-625`、`.history-tabs button.active` `src/index.css:689-693`）で、実際の色値から算出したコントラスト比が**2.41:1**。WCAG AA通常文字基準の4.5:1を大きく下回る。
  - 計算根拠: 相対輝度 L(accent)=0.385、L(white)=1.0 → (1.0+0.05)/(0.385+0.05)=2.41
  - 同じ色ペアはライトテーマ（`--accent:#2f6feb`）では4.57:1でぎりぎり基準内（[4]参照）。
- 再現手順: 1. `document.documentElement.dataset.theme='dark'`にする 2. 検索画面の「フォルダを作成」ボタン、または単語詳細画面の「この語についてAIに聞く」ボタン、またはチャット画面の自分の発言バブルを見る 3. 白文字の視認性が明らかにライトテーマ版より低い
- 証拠: `docs/review/agents/screenshots/visual/detail-dark.png`（「この語についてAIに聞く」ボタン）、`chat-dark.png`（自分の発言バブル「テスト質問です」）、`history-dark.png`（「重み付けビュー」アクティブタブ）
- 影響: ダークテーマ利用者（低視力・弱視含む）がボタンラベルやユーザー発言を読み取りにくい。3箇所とも同一パターンのため、同時に見つかった単発の誤りではなくトークン設計の構造的な穴。**エージェント1（アクセシビリティ）の[2]と同一の指摘（コントラスト比の計算結果も一致）。**
- 確信度: 確認済み（計算・スクリーンショット両方で確認）

## 確認できなかったこと
- **`.chat-spinner`のローディング状態の実際の見た目**: AI応答モックが即座に返るため、スピナーが表示されている瞬間のスクリーンショットは撮れなかった（[9]は色定義のコードレビューのみ）。
- **`.chat-error`が実際に画面に表示された状態のスクリーンショット**: エラーを意図的に発生させるテストケースを用意しなかったため、[2]の指摘は色値の計算のみに基づく。
- **`.toast` / `.toast-error`（トースト通知）の実際の見た目**: `globalError`を発生させるシナリオを再現しなかったため未撮影。
- **`.skeleton`（ローディングスケルトン）の見た目**: IndexedDBからの読み込みが速すぎてスケルトン表示状態を撮影できなかった。
- **LocalFolderPanelのフォルダ選択後・同期中の状態**: File System Access APIのネイティブダイアログはヘッドレスブラウザから自動操作できないため未検証。
- **狭い画面幅（モバイル相当）でのレイアウト**: 依頼範囲がPC画面（`src/ui/pc/`）のため1440×900のみで検証し、レスポンシブ崩れは対象外・未検証。
- **実際のWebフォント（BIZ UDPGothic / Noto Sans JP）がテスト実行環境に実在するか**: フォントが読み込めずフォールバックフォントで描画されていた場合、タイポグラフィの見え方評価がわずかに実環境とずれている可能性がある（`document.fonts.ready`は待機したが、フォント自体の存在確認はしていない）。
- **デッドCSS調査の網羅性の限界**: grepの部分一致検索を用いたため、短いクラス名が別の長いクラス名の一部として偶然マッチし、「使用あり」と誤判定される可能性が理論上残る（`.chat-message-user`のケースは手動で個別確認済みだが、全80件超について同水準の手動確認はしていない）。
- **`playwright.config.ts`のwebServer機能自体の安定性**: 当初`webServer`設定（`npm run build && npm run preview`を自動起動）を使ったところ、テスト実行中にサーバーが`ERR_CONNECTION_REFUSED`で断続的に落ちる現象が発生した（原因未特定。ポート競合の可能性はあるが確証なし。**エージェント3の報告[8]にある通り、複数エージェントが同一ポート4173を同時使用したことによる競合が濃厚**）。回避策として手動で`vite preview`を先に起動し固定ポートで安定運用したため、本調査の結果自体には影響していないが、この不安定性そのものは本来のビジュアル検証の対象外であり原因調査もしていない。
