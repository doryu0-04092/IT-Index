# プロンプト設計・回帰ケース集

- 版: 1.2（2026-07-29）
- 前提: [要件定義書](./requirements.md) §5.3 / [AIクライアント設計](./ai-client.md)

## 0. この文書の目的

`docs/ai-client.md` はプロンプトの**契約**（何を渡し、何を受け取るか）を定める。本文書は一段下のレベルで、**個々のプロンプト文言がなぜその形になっているか**と、**過去に見つかった誤動作の具体例（回帰ケース）**を記録する。

**設計ルール（最重要）**: プロンプトの挙動に不具合が見つかったとき、対応を**その場限りの文言パッチ**で終わらせない。必ず次の2つをセットで行う。

1. 修正後の文言を、対応するプロンプトのセクションに反映する
2. その不具合の入力・誤った出力・修正後の文言を、下記「回帰ケース」として本文書に追記する

回帰ケースが無いまま文言だけ直すと、次に似た不具合が出たときに「前にも似たことがあった気がする」以上の手がかりが残らず、また一から場当たり的に直すことになる（[ai-client.md §2](./ai-client.md)「これ/この」問題の経緯を参照——この文書は、その経緯で得た教訓を制度化したもの）。

**設計ルール（文脈の渡し方）**: 利用者の発言（`ChatMessageRecord.content`）には、文脈付与のための文字列を混ぜない。文脈は必ずシステムプロンプト（`system`）側に置く。理由は [ai-client.md §2](./ai-client.md) 参照——会話履歴を汚染しない、話題変更時に差し替えるだけで済む、分配統合に渡る内容が利用者の発言そのままになる、の3点。

## 2. 「現在の話題」ブロック

### 契約

`SubjectContext`（[ai-client.md §2](./ai-client.md)参照）から、次のいずれかを生成し `CHAT_SYSTEM_PROMPT` の末尾に追加する。

- `mode: 'term'`: 用語名・分野・読み・既存の初期説明・既存のAI補足（あれば）・指示語の解決先の指定
- `mode: 'free'`: `seedQuery` があればそれを参考情報として、無ければ「自由な質問」である旨のみ

### 回帰ケース

#### ケース1: 指示語（これ・この）が別の対象を指していると誤読される

- **状況**: 用語詳細画面「TCP/IP」から「この語についてAIに聞く」でチャットを開始し、最初の質問として「これはどういうもの？」と送る
- **誤った実装（初版）**: システムプロンプトに文脈を渡さず、ユーザー発言にも「〇〇についての質問です。」を添えるのみ、または一切添えない
- **誤った出力**: AIが「これ」を、会話に一切登場していない別のコマンドやエラーメッセージのことだと解釈し、的外れな回答を返す
- **原因**: 「〇〇についての質問です」という一文は話題の**説明**であり、直後の指示語（これ・この）の**指し先**として文法的に接続されていなかった
- **修正後の文言（「現在の話題」ブロック末尾）**:
  ```
  この対話中「これ」「この」等の指示語は、断りが無い限り「${label}」を指すものとして扱ってください。
  ```
- **確認方法**: 用語モードで開始し、最初のメッセージに指示語を含む質問（例:「これはどういうもの？」「これの使い道は？」）を送り、その用語について回答しているかを確認する

## 3. `DISTRIBUTION_SYSTEM_PROMPT` / `MERGE_SYSTEM_PROMPT`

契約は [ai-client.md §3〜4](./ai-client.md) を参照。

### 設計メモ: `summary`（初期説明）フィールドの追加（2026-07-29）

新規登録される語にも初期説明を持たせるため、出力に `summary`（一文の要約）を追加した（要件定義書§5.2「なぜAIが初期説明に触れないのか」の例外、[ai-client.md §4.3](./ai-client.md)）。プロンプト設計上の注意点:

- `summary` と `draftBody` は役割が違う（前者は一文の要約、後者は前提知識・具体例を含む詳しい説明）。**プロンプトで明示的に「重複して長く書くな」と釘を刺していないと、AIは同じ内容を両方に書きがち**（一般的なLLMの傾向として、区別が曖昧な2つのフィールドがあると片方をもう片方の縮小コピーにしてしまう）。`DISTRIBUTION_SYSTEM_PROMPT` のルール節に明記済み
- `summary` は既存語では無視される（既存語の初期説明は不変のため）。AI自身はどの語が新規でどの語が既存かを知らない（`distribution.ts` 側がクライアント側で判定する）ので、**isTerm:true の全項目に一律で書かせる**——「新規語だけ書け」という条件をAI側の判断に委ねると、判定を誤って空文字を返すリスクがある

### 回帰ケース

#### ケース1: AIの説明の中で触れただけの語まで新規登録候補になる

- **状況**: 「TCP/IPって何？」という質問に対し、AIが説明の中で「ルーティング」という別の（実在する）IT用語にも触れる
- **誤った実装（初版）**: 分配統合は `isTerm` のみで判定していたため、「ルーティング」も `isTerm: true` として切り出され、辞書に無ければ新規登録候補として承認画面に並んだ
- **誤った結果**: 利用者が尋ねてもいない語が、会話のたびに複数、新規登録候補として提示される。承認画面が「本当に知りたかった語」以外のノイズで埋まる
- **原因**: `isTerm`（IT用語かどうか）と「利用者が明示的に尋ねたかどうか」は別の軸なのに、後者を判定していなかった
- **修正**: `askedByUser` フィールドを追加し（[ai-client.md §4.1](./ai-client.md)）、辞書に無い語（新規登録になる語）は `askedByUser: false` の場合に候補から除外するようにした（`src/ai/distribution.ts`）。既存語への追記は対象外（既存語の更新は非破壊ルールで既に安全なため、絞り込む理由が無い）
- **確認方法**: ある用語について質問し、AIの回答が別の実在用語に言及する会話をコミットして、その別用語が（辞書に無い場合は）承認画面に出ないことを確認する。既存語であれば通常どおり更新候補に出ることも合わせて確認する
