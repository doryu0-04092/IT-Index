# IT-Index 要件定義書

- 版: 1.4（2026-07-30）
- リポジトリ: https://github.com/doryu0-04092/IT-Index

---

## 1. このアプリの位置づけ

> **未経験のITエンジニアが、不慣れなIT用語を最速で調べられる環境を構築する。**
> **同時に、各用語や苦手分野を克服するために使う「辞書を兼ねた学習ツール」とする。**

**この二重の目的が、本設計のすべての起点になっている。** 単なる辞書でも、単なる学習アプリでもない。

| 目的 | それを実現する設計 |
|---|---|
| **最速で調べる** | 検索は完全ローカル演算（通信なし・無料・無制限）／簡潔な `summary` は「思い出す用」／**かな入力だけで漢字語も英字語も引ける** |
| **苦手を克服する** | AI補足は「分からなかった自分が、分かるまでに必要だった情報」の記録／質問回数の重み付けで**まだ定着していない語**を可視化／減衰により**克服した語は自然に沈む** |

### 想定する利用者の状態

対象は**未経験のITエンジニア**。次の状態を前提に置く。

- 見出し語の**漢字が読めない**（「冗長化」を「じょうちょうか」と読めない）
- 略語の**読み方を知らない**（`API` を「えーぴーあい」と言えない）
- **そもそも前提知識が無い**ので、一般的な辞書の定義文を読んでも分からない

読み検索の設計（§5.1）とAI補足の設計（§5.2）は、この3点から直接導かれている。

### 既存手段との違い

| 手段 | 足りないもの |
|---|---|
| 一般的なIT用語辞典 | 定義は載っているが、**前提知識が無いと読めない**。自分がどこで詰まったかは残らない |
| ChatGPT等に都度聞く | 毎回ゼロから。**同じ語を3回聞いても3回とも同じ説明**が返り、自分用に蓄積されない。何を聞いたかも残らない |
| **IT-Index** | **聞くほど自分専用に育ち、何を繰り返し聞いたかが弱点として可視化される** |

## 2. 用語の定義

本書で使う独自用語。実装・他文書でも同じ語を使う。

| 用語 | 意味 |
|---|---|
| **初期説明**（`summary`） | 本人が用意した簡潔な説明。**思い出す用。AIは書き換えない**（不変） |
| **AI補足**（`notes.body`） | AIが書く、単独で読めば理解できる完結した説明。**理解する用。使うたびに育つ** |
| **確定** | チャットの会話を終わりと見なし、AI補足へ反映する操作 |
| **分配統合** | 1つの会話を用語ごとに切り分け、それぞれのAI補足へ配って重複を落として統合すること |
| **決定的マージ** | AIを使わず、規則だけで行う同期の突き合わせ |
| **シード** | 初期データ。`public/seed/terms.json` |

## 3. 対象環境

| 項目 | 内容 |
|---|---|
| 形態 | **Androidアプリ（Capacitor）／PCデスクトップアプリ（Electron）**。開発・検証はブラウザでも動く（2026-08-02改訂） |
| 対応OS・ブラウザ | **Android／PC（Windows）**。ブラウザで開く場合は Chrome・Edge |
| **非対応** | **iPhone・iPad・macOS Safari。Firefox は動作するが鍵の保存機能のみ制限** |
| サーバー | **料金のかかる外部サーバーを持たない**（2026-08-02に表現を訂正）。端末間同期は同一LAN内の直接通信で完結し、**中継サーバーすら不要** |
| 外部サービス | Claude API（AI・必須）／Google Drive API（同期・任意・2026-07-27時点で未設定）。**いずれも利用者自身の資格情報を使う** |

### 非対応を明記する理由

**「なぜ iPhone で動かないのか」を毎回説明しないため。** Apple 系は今回のスコープから明示的に外している（判断の経緯は [decisions/](./decisions/) 参照予定）。

非対応環境で開かれた場合は、**その旨を明示するバナーを表示する**（無言だと「壊れている」と受け取られる）。

## 4. 全体像

```
【無料・無制限】検索 … ローカル演算のみ。通信しない
      │
      ├─ 見つかった ─→ 用語詳細（初期説明 ＋ AI補足 ＋ 図）
      │
      └─ 見つからない ─→ [ AIに聞く ] ← 利用者が明示的に押す
                              ↓
                        チャット（複数ターン）
                              ↓
                        【確定】分配統合 ─┬→ 既知の語のAI補足に統合
                                          ├→ 未知の語は登録可否を確認
                                          └→ 各語に「聞いた記録」を1件ずつ
                              ↓
                        重み付けビュー／時系列ビュー
                              ↓
                        端末間同期（手動ファイル書き出し。Google Drive同期は任意のオプション）
```

**通信が発生するのはチャット以降だけ。** 検索・閲覧・履歴はすべてオフラインかつ無料で動く。

## 5. 機能要件

### 5.1 【重点】用語検索 — かな入力だけで漢字も英字も引ける

**目的「最速で調べる」の中核。**

#### 方針: 最小限の正規化 ＋ 類似度スコアの順位付け

除外ルールを積み上げると例外が際限なく増える。**「候補から外す」のではなく「スコアの低い順位に落とす」**ことで、ノイズを抑えつつ取りこぼしを防ぐ。

**第1段 — 正規化はこの3つだけ**

| ルール | 例 |
|---|---|
| ひらがな ⇄ カタカナ を統一 | `さーば` ＝ `サーバ` |
| 全角 ⇄ 半角（英数記号） | `ＴＣＰ` ＝ `TCP` |
| 英字の大小を無視 | `tcp` ＝ `TCP` |

**なぜこの3つだけなのか。** これらは**文字コードが完全に別**で、類似度スコアでは絶対に拾えない（`さーば` と `サーバ` は全文字が別コードなので類似度0）。逆に言えば、スコアで拾えるものは正規化しなくてよい。

**第2段 — 残りはすべてスコアに任せる**

| ずれ | 例 | 文字差 |
|---|---|---|
| 長音 | `サーバー` ↔ `サーバ` | 1 |
| 記号 | `TCP/IP` ↔ `TCPIP` | 1 |
| 漢数字 | `三層` ↔ `3層` | 1 |
| 送り仮名 | `割り当て` ↔ `割当` | 1 |
| タイプミス | `TCP/PI` ↔ `TCP/IP` | 1 |

いずれも1〜2文字差なので、スコアが自然に上位へ持ち上げる。**個別ルールを書かない。**

スコアは **2-gram の Dice 係数**を基礎に、完全一致／前方一致／部分一致で加点する。

#### 漢字を変換しない代わりに、読みを全語に持たせる

漢字は字面でしか当たらない。そこを読みで埋める。**漢字語にも英字語にも読みを付ける**（詳細は [seed-format.md](./seed-format.md) §3）。

読みが揺れる略語（SQL＝エスキューエル／シークェル）は**主要な1つだけ**を持つ。非代表的な読みしか知らない場合は、**英字で直接引く**か**チャットで聞く**の2段で受け止める。

#### 見つからない時にAIを自動で呼ばない

順位付けは必ず何かを返すので「候補ゼロ」は発生しない。したがって「ゼロ件ならAIを呼ぶ」という自動化は成立しない。

**そこで、検索からAIを自動で呼ばない設計にする。** 該当する候補が無いときに `[ AIに聞く ]` ボタンを出し、**利用者が押したときだけ**チャットへ進む。

> **これにより、タイプミスで勝手に課金される事故が構造的に起きない。**

### 5.2 【重点】辞書が引くたびに育つ — 2枠分離

**目的「苦手を克服する」の中核。**

用語詳細は3段構成。

```
┌────────────────────────────────┐
│ TCP/IP        ティーシーピーアイピー  │
├────────────────────────────────┤
│ ① 初期説明（本人準備・簡潔・不変）        │ ← AIは書き換えない
│    通信の取り決めを層に分けた規約の集まり。  │
│                                │
│ ── 理解のために調べたこと ──          │
│ ② AI補足テキスト（統合されて育つ）        │ ← ここだけAIが書く
│    単独で読んで理解できる完結した文章       │
│                                │
│ ── 図 ──                        │
│ ③ Mermaid 図（別枠）                │ ← 壊れてもテキストは無傷
└────────────────────────────────┘
```

| 枠 | 目的 | 性質 |
|---|---|---|
| ① 初期説明 | **思い出す** | 簡潔。分かる人が見れば足りる。**不変** |
| ② AI補足 | **理解する** | 単独で読んで理解できる完結した文章。**育つ** |
| ③ 図 | 理解を補助 | Mermaid。テキストとは別フィールド |

#### なぜ2枠に分けるのか

**役割が違うものを1つの本文に混ぜると、両方が中途半端になる。**

- 思い出すための説明は簡潔でなければ役に立たない（長いと探す時間がかかる）
- 理解するための説明は前提知識・具体例・つまずきどころを含むので長くなる

分けることで、**それぞれが自分の役割に最適化できる。**

#### なぜAIが初期説明に触れないのか

**構造的に事故を防ぐため。** 分離していなければ、初期データを更新配信したときに利用者が蓄積したAI補足を上書きしかねない。テーブルごと分けてあるので、**初期データを何度差し替えてもAI補足は無傷**。特別な保護ルールが要らない。

**例外（2026-07-29追加）: AIが新規登録する語だけは、登録の瞬間にAIが初期説明を書く。** 既存語（本人がシードとして用意した語）の初期説明は従来どおり不変・AIは一切触れない。しかしAIチャットから新しく辞書に追加される語には、そもそも「本人が用意した」初期説明が存在しない——**無いものを保護する必要は無く**、代わりに初期説明という枠自体が空のまま残ってしまうと、用語詳細画面でその語だけ「思い出す用」の短い説明が永遠に無いことになる。そこで分配統合の出力に一文の要約（`summary`）を追加させ、新規登録時にだけ使う（[ai-client.md §4.1](./ai-client.md)）。**登録された後は、この初期説明も他の語と同じく不変**——以後の統合（merge）では書き換えない。

#### AI補足は初期説明を前提にしない

内容が初期説明と重なっても構わない。**それだけ読めば完結する**ように書かせる。

- 前提知識、具体例、つまずきやすい点を含める
- 「分からなかった自分が、分かるようになるまでに必要だった情報」の記録
- **同じ用語でも人によって中身が変わる、パーソナルな学習記録になる**

前提にしないことで、初期説明をAIへの入力に渡す必要が無くなり、プロンプトが単純になる。「初期説明と重複するな」という制約も消えるので、統合時に情報が削られる圧力が下がる。

#### 図をテキストと別フィールドにする理由

**構文エラーの隔離。** AIが壊れた Mermaid を返したとき、

| 持ち方 | 結果 |
|---|---|
| 本文に埋め込む | 描画で例外 → **その用語の補足が丸ごと見えなくなる** |
| **別フィールド（採用）** | **テキストは構造的に無傷。** 壊れた図だけ差し替えれば済む |

フォールバック実装で守るのではなく、**データ構造で保証する。**

図の形式は **Mermaid（テキスト）**。SVGの直接生成は品質が不安定で、かつ `<script>` を含められるためXSSの経路になるので採らない。外部画像の引用は著作権・リンク切れ・CSP設計との衝突のため採らない。

### 5.3 【重点】AIチャットと分配統合

#### チャットは辞書と分ける。統合はセッション単位

対話は複数ターン続き、**会話全体が終わってから1回だけ**AI補足に反映される。

**1メッセージごとに統合すると、対話途中の断片が何度も統合され、繰り返すほど情報が痩せる。** 会話が終わってから1回だけ統合すれば、API呼び出しも劣化も1回で済む。

**確定（＝統合）は明示的な確定操作（確定ボタン）のみで起きる（2026-07-30改訂）。**

**旧方針（〜2026-07-29）**: 確定トリガーは3つあった——①別の用語のチャットを開いた、②最終操作から15分経過、③明示的な確定操作。②のためにタブを閉じても効くよう起動時の放置セッション回収（④）も持っていた。

**2026-07-30改訂（ローカルデータ層導入。[local-data.md](./local-data.md) §11）**: ①②④の自動トリガーを廃止した。理由は、Claude Code によるローカルファイル編集を確定処理（取り込み→AI要約→書き出し）の起点に組み込んだため——確定タイミングが自動で決まると、ファイルへの書き出しタイミングも予測不能になり、Claude Code の編集と衝突する窓が広がる。確定していないセッションはホームの「AIによる単語更新待ち」一覧に残り続け、利用者が明示的に確定するまでそのままになる。確定処理は**冪等**とし、同じセッションを2回確定してもAI補足が二重にならないようにする。

#### チャットの主題（SubjectContext）— AIに推測させず、利用者が選ぶ

**「AIがどの用語について聞かれているか」を、AI自身の推測に委ねない。** 主題は次の2つのモードのどちらかとして必ず確定させ、利用者の操作で選ばれたものだけを使う。

| モード | 成立条件 | 内容 |
|---|---|---|
| **用語モード** | `termId` が確定している | 用語詳細画面からのチャット開始、または検索結果一覧で**利用者が特定の行を明示的に選んで**開始した場合のみ。辞書に既にある初期説明・AI補足を文脈として使える |
| **自由モード** | `termId` が未確定 | 検索結果を選ばずに「AIに聞く」を押した場合。検索欄の文字列は参考情報として扱うが、確定した主題としては扱わない |

検索結果の最上位候補への**自動ひも付けはしない**。類似度スコアはあくまで検索の順位付け用であり、「これがユーザーの聞きたい語だろう」とAI側やアプリ側が推測に使う情報源にはしない（§5.1「除外ルールを積み上げない」と同じ理由——推測に頼ると、外れたときの原因が利用者から見えなくなる）。

チャット画面には常に現在の主題を示す表示（用語モードなら用語名、自由モードならその旨）を出し、**利用者はいつでも `[話題を変える]` で明示的に選び直せる。** これはUI側の制約によって「AIが話題を誤読する余地」自体を無くすアプローチであり、[ai-client.md §2](./ai-client.md)の文脈付与の設計とセットになっている。

**2026-07-30改訂**: 話題を変えても、それ以前の会話は自動で確定されない（旧トリガー①は廃止済み。上記「確定のトリガー」参照）。元のセッションは `open` のまま「AIによる単語更新待ち」一覧に残り、利用者が明示的に確定するまでそのままになる。確定時の統合は`MERGE_SYSTEM_PROMPT`（[ai-client.md §3](./ai-client.md)）により「既存の情報を勝手に削らない、重複整理のみ許可、要約して薄めない」という制約の下で行われるため、確定を後回しにしても情報が失われる構造的なリスクは無い。

複数用語にまたがる比較質問（例:「AとBの違いは」）へのグラウンディング対応は、現時点では対象外とし、自由モードとして扱う（将来の拡張候補として[ai-client.md §6](./ai-client.md)に記録）。

#### 1つの会話を複数の用語に分配する

チャットは自由に始められ、1つの会話で複数の用語に触れてよい。

```
1つの会話 ──【確定】──┬→ TCP/IP      のAI補足に追記
                      ├→ ルーティング  のAI補足に追記
                      └→ MTU（辞書に無い）→ 新規登録
```

これで「自由チャットは統合先が決まらない」問題が解ける。

#### 分配は常に自動でDBへ反映される（承認画面は廃止。2026-07-30決定）

**旧方針（2026-07-27〜29）**: 分配統合は必ず承認画面を挟み、利用者がチェックを付けた語だけをDBへ反映していた。AIが会話を誤って切り分けると関係ない用語に無関係な補足が付くため、という理由だった。

**2026-07-30改訂**: 承認画面を廃止し、確定と同時に常に自動でDBへ反映するようにした。手作業のチェックという手間を無くす代わりに、**「何を自動反映してよいか」を承認画面ではなく、下記2つの構造的なルールで決める。**

1. **新規登録**: 利用者自身が明示的に尋ねた語だけ（下記「新規登録は、利用者が明示的に尋ねた語だけ」）
2. **既存語への追記**: 利用者自身が尋ねたか、他の語についての会話で触れられただけかによって、設定で選んだ範囲だけ（下記「既存語への自動反映は設定で選ぶ」）

いずれの経路でも、書き込み先は`notes`（AI補足）と、新規登録の場合のみ`terms`であり、**既存語の初期説明（`summary`）は一切書き換えない**（§5.2）。また`MERGE_SYSTEM_PROMPT`の「削らない・重複整理のみ・要約して薄めない」というルール（本節上部）により、自動反映そのものによって既存の情報が失われることは無い。承認画面が担っていた「人間の目でのチェック」は、この2つのルールと、利用者がいつでも用語詳細画面でAI補足を読んで気づける、という構造に置き換わった。

#### 用語でないものを登録しない: `isTerm` による除外

雑談から「今日の天気」のような語を抽出してしまう可能性がある。分配統合の出力に **`isTerm`（IT用語かどうか）** を持たせ、偽の候補は最初から除外する。

#### 新規登録は、利用者が明示的に尋ねた語だけ（2026-07-29決定）

AIが1つの語（例: TCP/IP）を説明する過程で、別の語（例: ルーティング）に触れることは自然に起きる。**その触れられただけの語まで新規登録すると、1回の会話で無関係な新規語が何件も勝手に登録される。** これは「用語でないものを登録しない」（上記の`isTerm`）とは別の問題——ルーティングは実在するIT用語であり`isTerm`は true になるが、利用者はそれについて尋ねていない。

そこで、分配統合の出力に **`askedByUser`（利用者自身がその語について明示的に尋ねたか）** を追加する。**辞書に無い語（＝新規登録になる語）は `askedByUser` が true の場合のみ新規登録の対象にする。** この絞り込みは下記の設定（既存語向け）とは独立で、**新規登録には常にこのルール1本だけが適用される**——設定を「他の語の情報も自動更新する」にしても、無関係な新規語が増えることはない。

#### 既存語への自動反映は設定で選ぶ（2026-07-29決定 → 2026-07-30改訂）

既存語への追記（統合）は、新規登録と違って`MERGE_SYSTEM_PROMPT`の非破壊ルールで安全性が構造的に担保されている。とはいえ「利用者が尋ねてもいない語の内容が、会話のたびに勝手に書き換わる」ことへの安心感は人によって違う。そこで**設定画面**（⚙）に次の2択を置き、既存語への自動反映の範囲を利用者が選べるようにする。**既定は前者。**

| モード | 内容 |
|---|---|
| **自分が検索・質問した語だけ自動更新する（既定）** | `askedByUser: true` の既存語だけAI補足に追記する。他の語の説明中にただ触れられただけの既存語（`askedByUser: false`）は反映しない |
| **他の語について調べた際に出てきた情報も自動更新する** | `askedByUser` の値に関わらず、分配統合の候補に残った既存語への追記をすべて反映する |

この設定は既存語だけに効く。新規登録の判定（上記）には影響しない。

#### 用語間の移動は「選択して引く」

補足の中の分からない語をなぞって選択し、`[この語を引く]` から検索へ送る。

**本文中の用語を自動リンク化しない。** 自動リンクは「IP が TCP/IP の内部にマッチして二重リンク」「キー・テーブル・ポートなど日常語が乱リンク」「描画のたびに全用語をスキャンして重い」の3問題を必ず生む。**利用者が範囲を決める方式なら、3つとも起きない。**

### 5.4 【重点】重み付け — 苦手分野の可視化

#### 数えるのは「チャットで解説を求めた回数」と「検索して用語詳細を確定した回数」（2026-07-29改訂）

**改訂前の方針**: 検索窓からの引きも、一覧からの閲覧も数えない。理由は「検索は思い出せているかの確認でしかなく、タイプミスや流し見も混ざる。『分からなくて聞いた』という事実の方が、定着していない度合いを正確に表す」というもので、AIチャットで解説を求めた回数だけを数えていた。

**改訂後**: ローカル検索も対象に含める。ただし「検索窓に入力しただけ」「一覧をただ眺めただけ」は従来どおり数えない——**検索結果から実際に1つの語を選んで用語詳細画面を開いた瞬間**だけを「確定」とみなす。タイプミスや流し見（結果一覧を見ただけで何も選ばない）はここでも除外されるため、上記の懸念（ノイズが混ざる）は変わらず避けられる。

**AIチャットで確定した語のほうを強く扱う**: 「分からなくて聞いた」という事実の強さは変わらないため、AIチャット確定はローカル検索確定より重い（既定3倍）重みで加算する（下記の式の `w_i` 参照）。検索して見に行っただけの語（軽い関心・思い出す用の確認）と、AIに聞くところまで踏み込んだ語（分からなかった）を、同じ「定着していない度合い」の指標の中で強弱をつけて扱う。

複数の語について一度に聞いた場合は、分配統合で解説が付いた**全ての語に1回ずつ**加算する（AIチャット確定側は従来どおり）。

#### 減衰は「時間」ではなく「その後の質問回数」で効かせる

単純な累計だと、一度たくさん聞いた語が永久に上位に居座る。もう理解できているのに表示され続けてしまう。**そこで減衰を入れるが、時計は使わない。**

| 減衰の軸 | 問題 |
|---|---|
| 経過日数 | **使わなかった期間だけでスコアが落ちる。** 学習していないのに「定着した」ことになる。加えて `now()` に依存するため**端末ごとに結果がずれる** |
| **その後の質問回数（採用）** | **使っている間だけ順位が動く。** 放置しても減らない。記録だけから決まるので**完全に決定的** |

```
score(語) = Σ  w_i · r^(N − i)          r = 0.5^(1/H)
          その語が聞かれた／確定された各イベント i について

  N = 全体のイベント総数（AIチャット確定＋ローカル検索確定）
  i = そのイベントの通し番号
  H = 半減期（既定50問）
  w_i = イベントの重み（AIチャット確定=3、ローカル検索確定=1。2026-07-29追加）
```

**意味**: 「最後に聞いてから、他のイベントが何回積み重なったか」で減る。他をたくさん聞けば、聞かれなかった語は自然に沈む。**克服した語は表示から消えていく。** AIチャット確定と検索確定は同じ通し番号を共有する（同じ減衰時計の上で動く）が、加算される重みが異なる。

通し番号は `(時刻, id)` の複合キーで決める。時刻だけでは端末間のずれで順序が変わるため、`id` をタイブレークに使って**どの端末でも同じ順序**にする。

#### 履歴の見せ方

| ビュー | 内容 |
|---|---|
| **重み付けビュー** | 上のスコア順。「最近も繰り返し聞いている＝まだ定着していない語」 |
| **時系列ビュー** | 聞いた順（新しい順）。**いつ何について聞いたかの学習記録** |

### 5.5 【重点】サーバーを持たない同期

自前のサーバーを立てず、端末間を同期する。

> **2026-07-27 方針転換**: 当初は Google Drive（appDataFolder）のみを同期手段とする方針だったが、Google Cloud Console 側の設定（OAuth同意画面の「テスト」ステータス維持、審査対応など）が個人開発の運用として継続しづらいと判断し、**手動でのファイル書き出し／取り込みを主手段にする**。Drive同期のコード・設計自体は削除せず、後で有効化できるよう休眠させてある（[drive-sync.md](./drive-sync.md)）。以下の設計（端末ごとにファイルを分ける・決定的マージ・AIの役割）は輸送手段に依存しないため、Drive経由でも手動ファイルでもそのまま使う。詳細は [manual-sync.md](./manual-sync.md)。

> **2026-08-02 方針転換**: 主手段を **同一LAN内のQRペアリング（直接HTTP通信）** に切り替えた。QRを表示した側がローカルHTTPサーバーを立てて待ち受け、読み取った側が接続する。中継サーバー・アカウント・インターネット接続のいずれも不要。
>
> **これを可能にしたのはPC版のアプリ化（Electron）である。** ブラウザのページは「接続を待ち受ける」ことも mDNSで相手を探すことも、httpsページから `http://192.168.x.x` へ繋ぐこともできない。LocalSendやSyncthingが設定なしで繋がるのは両側がネイティブアプリだからで、**PC版がブラウザである限りこの経路は原理的に作れなかった。** 検討の過程でQR単体・WebRTC・無料の外部中継を順に検討して却下している（経緯は `agent-kit/log/decisions/`）。

**輸送手段:**

| 手段 | やり方 | 状態 |
|---|---|---|
| **LAN内QRペアリング（主手段）** | 片方がQRを表示（接続先URL＋使い捨て鍵）→ もう片方がカメラで読む → 双方が全量スナップショットを暗号化して送り合いマージする。**どちらが表示側でも結果は同一** | 実装済み（2026-08-02） |
| **手動ファイル書き出し（フォールバック）** | 端末Aで `device-<A>.json` をダウンロード → 何らかの方法（メール・USB・クラウドストレージ等）で端末Bへ移す → 端末Bでアプリに読み込ませる | 実装済み。**LANが使えない状況の逃げ道として常設** |
| Google Drive（任意） | 利用者自身の Google Drive（アプリ専用領域）を経由して自動化する | 実装済みだがGoogle Cloud未設定のため未疎通。休眠中 |

#### QRに載せるのは鍵とアドレスだけ

本文はQRに載せない（載せると容量が足りない）。QRが運ぶのは約80バイトの `{ url, 32バイトの鍵 }` のみで、本文はLAN内のHTTPで送る。

鍵は**QRでしか渡らない使い捨て**で、認証と暗号化を兼ねる。平文HTTPでも中身は読めず、同一LAN上の第三者がポートを叩いても復号も生成もできない。**接続先はプライベートアドレスに限定する**——ここを緩めると、攻撃者が用意したQR（任意のURL＋攻撃者自身の鍵）を読ませるだけで全スナップショットを外部へ送信させられる（鍵も攻撃者のものなので暗号化は防御にならない）。

#### 端末ごとにファイルを分ける

```
appDataFolder/
  device-<A>.json    ← 端末Aだけが書く。他は読むだけ
  device-<B>.json    ← 端末Bだけが書く
```

**なぜ共有1ファイルにしないのか。** 全端末が1つのファイルを読み書きすると、必ず更新が消える。

```
端末A: 読む(v1) → 統合 → 書く(v2)
端末B: 読む(v1) → 統合 → 書く(v2')   ← Aの変更を上書き
```

「読んで統合してから書く」形自体は正しいが、**それだけでは防げない**。AとBが同じ版を読んだ時点で、後から書いた方が勝ってしまう。

**端末ごとにファイルを分けると、各ファイルの書き手が1台しかいないので取り合いが起きない。** 更新消失が構造的に発生せず、バージョン確認の仕組みも要らなくなる。1つのファイルが壊れても他は無傷、という副次効果もある。

#### 各ファイルには「その端末発の変更だけ」を書く

全量を書くと端末数だけ重複して膨らむ。**最後に編集した端末を記録し、自分が編集したものだけを自分のファイルに書く。** これで各ファイルが真の差分になる。

#### 読み込み＝全ファイルをマージ

**マージの土台は決定的なコードで書く。**

- AI補足は更新時刻が新しい方を採用
- 削除は物理削除せず削除印を残す（消したものが復活する事故を防ぐ）
- 聞いた記録は追記のみなので `id` で和集合

**AIは「決定的コードでは判断できない2箇所」にだけ使う。**

| 場面 | コードの限界 | AIの役割 |
|---|---|---|
| 表記ゆれ | 別端末で「オブジェクト指向」「オブジェクト志向」を登録。文字列一致では同一と判定できない | 同一概念かを判定 |
| 同じ語の両端更新 | 新しい方を採ると片方の本文を捨てる | 両方を統合した本文を生成 |

**AIの出力は提案として保留し、承認するまで適用しない。** AIが使えない（鍵が無い）場合も決定的マージだけで動く。**同期の必須要素にしない。**

### 5.6 【重点】セキュリティ — 「漏れても被害が有限」を先に作る

APIキーは利用者自身のものをブラウザで扱う。**「漏らさない」だけでは足りないので、先に被害を有限化する。**

| 層 | 内容 | 効き方 |
|---|---|---|
| **1. 支出上限** | 専用ワークスペースに**支出上限付きのAPIキー**を発行して使う | **漏れても損失が上限で止まる。** 防止策が全て破られた後に効く唯一の層 |
| **2. パスキー紐付け** | 保存する場合、**WebAuthn PRF** でパスキー（Windows Hello / Android生体認証）から鍵を導出し暗号化 | **暗号化データを他端末にコピーしても復号できない。** パスフレーズを覚える必要もない |
| **3. 既定は保存しない** | セッション中のみメモリ保持。保存は明示的なオプトイン | そもそも残さない |
| **4. XSSを通さない** | CSP厳格化（`script-src 'self'`）／依存を最小に／`innerHTML` を使わない／AI出力はサニタイズ | **2までを無効化しうる唯一の経路。ここが本丸** |
| **5. 権限を最小に** | Drive は `drive.appdata` のみ。**利用者の既存ファイルには一切アクセスしない** | 事故時の影響範囲を絞る |
| **6. 鍵を同期対象外に** | Drive に上げるデータにAPIキーを含めない | 同期経路に鍵を流さない |

> **暗号化は本丸ではない。** XSS が通れば復号後の鍵はメモリから取れる。暗号化が守るのは「端末を他人が直接見た場合」であり、**本質的な防御は第4層**。第2層は多層防御の一層と位置づける。
